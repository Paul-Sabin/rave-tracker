## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Web service had not redeployed after Railway variables were saved**
- **Found during:** Task 3, first two verification attempts
- **Issue:** The app correctly redirected to `/verify-email?send_failed=1` and showed the red banner (proof that plan 20.1-02's failure-surfacing works), but no mail arrived and Railway showed no fresh error in the running container's log. Setting variables in the Railway UI does not itself trigger a restart of that container.
- **Fix:** A git push to `main` (unrelated - part of shipping the verification script) triggered Railway's auto-deploy-on-push, which started a fresh container (2026-08-23T10:12 UTC) that finally picked up the new env vars.
- **Files modified:** none (infrastructure timing issue, not code)
- **Verification:** Subsequent runs against the new container produced the real Brevo error in the log instead of a stale "not configured" state.
- **Committed in:** n/a (operational finding, documented here and in `what_happened`)

**2. [Rule 1 - Bug, third-party] Brevo authorised-IPs guard rejecting Railway's egress IP**
- **Found during:** Task 3, after the redeploy above
- **Issue:** Railway log showed `Brevo API error 401: {"message":"We have detected you are using an unrecognised IP address 152.55.176.106...","code":"unauthorized"}`. The API key was correct; Brevo's account-level authorised-IPs security feature was blocking the send.
- **Fix:** Human deactivated Brevo's authorised-IPs setting in the Brevo dashboard (outside this repo's control - no code or Railway variable change).
- **Files modified:** none
- **Verification:** Immediately after, the full 14/14 automated check passed and real mail arrived.
- **Committed in:** n/a (third-party dashboard configuration)
