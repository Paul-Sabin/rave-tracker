### `ra_tracker/services/email_sender.py` (service, request-response)

**Analog:** itself (existing `_send_via_api`) + `ra_tracker/services/notifier.py:436-445` for the "propagate the bool, don't swallow it" convention already used one layer up.

**Current defect — two occurrences, both must be fixed together:**
```python

# ra_tracker/services/email_sender.py:133 — inside is_email_configured(), SAME defect
```

Both read as "fall back to the SMTP password as the Brevo API key." Per RESEARCH.md Pitfall 1, these are non-interchangeable credential types managed in different parts of the Brevo dashboard. Fix: require `config.email.api_key` explicitly in both places; treat "SMTP password present but no API key" the same as "not configured" (`return False` / `return False` respectively), reusing the existing warning already present at line 95:
```python

    logger.warning("Brevo API key not configured (set BREVO_API_KEY)")
    return False
```

**Core pattern — `_send_via_api` (lines 89-126), the function to fix, not rewrite:**
```python
# ra_tracker/services/email_sender.py:89-126
def _send_via_api(to_email: str, subject: str, html_content: str) -> bool:
    """Send email via Brevo HTTP API."""
    config = get_config()
    api_key = config.email.api_key or config.email.password   # <-- fix: drop `or config.email.password`

    if not api_key:
        logger.warning("Brevo API key not configured (set BREVO_API_KEY)")
        return False

    from_email = config.email.from_address or config.email.username
    from_name = config.email.from_name

    payload = {
        "sender": {"name": from_name, "email": from_email},
        "to": [{"email": to_email}],
        "subject": subject,
        "htmlContent": html_content,
    }

    try:
        resp = requests.post(
            BREVO_API_URL,
            json=payload,
            headers={
                "api-key": api_key,
                "Content-Type": "application/json",
            },
            timeout=30,
        )
        if resp.status_code in (200, 201):
            logger.info(f"Sent email via Brevo API to {to_email}")
            return True
        else:
            logger.error(f"Brevo API error {resp.status_code}: {resp.text}")
            return False
    except Exception as e:
        logger.error(f"Failed to send email via Brevo API to {to_email}: {e}")
        return False
```
This function already matches Brevo's documented contract (payload shape, `api-key` header, 201 success) — do not rewrite the HTTP call, only the `api_key =` line and (per `is_email_configured`) the identical line at 133.

**Error handling pattern (already correct, keep):** every branch (`not api_key`, non-2xx status, exception) returns `False` and logs via `logger.warning`/`logger.error` — never raises to the caller. All 5 send functions (`send_notification_email`, `send_verification_email`, `send_password_reset_email`, `send_deletion_confirmation_email`, `send_recovery_confirmation_email`, at lines 138, 212, 257, 298, 338 respectively) already delegate to `_send_via_api` when `config.email.use_api` is true and return its boolean directly — no change needed to any of those five functions themselves, only to `_send_via_api` and `is_email_configured`.

**Boolean-propagation convention to imitate (from `notifier.py`, already correct):**
