<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| human -> Railway variable store | A new long-lived production secret is created and stored here |
| Brevo dashboard -> human clipboard -> Railway | The window in which the API key is most likely to be leaked (chat, notes, a commit) |
| deployed app -> external mailbox | The verification link is a signed, time-limited capability travelling over third-party infrastructure |
| admin browser -> /admin/audit-log | Audit rows containing user ids and IPs are exposed to whoever holds admin |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20.1-02 | Information Disclosure | The Brevo API key leaking into chat, the repo, or a commit while being transferred | mitigate | Task 2 instructs that the key is pasted only into the Railway field, and the resume signal asks for "variables set" rather than any value; Task 1 greps the outgoing diff for the `xkeysib`/`xsmtpsib` Brevo prefixes and asserts `ra-tracker/.env` is not staged |
| T-20.1-06 | Spoofing | An over-scoped or stale Brevo key, or the SMTP key used as the API key | mitigate | Task 2 names the exact dashboard tab, tells the human the SMTP key produces `401`, and Task 3 step 2 makes a wrong key visible immediately as the red failure banner instead of a silent non-delivery |
| T-20.1-13 | Information Disclosure | Verification link for the throwaway test account remaining valid after the test | accept | Tokens are `itsdangerous` time-limited (24h) and single-purpose; the optional cleanup step uses the app's own deletion flow |

| T-20.1-15 | Repudiation | Production audit log being trusted without ever being read | mitigate | Task 3 step 5 requires querying both the success and the failure filter, so the operator confirms the distinction exists in production data rather than only in tests |
</threat_model>
