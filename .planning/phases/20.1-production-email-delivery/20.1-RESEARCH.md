# Phase 20.1: Production Email Delivery - Research

**Researched:** 2026-08-22
**Domain:** Transactional email delivery on Railway (Brevo SMTP vs HTTP API), failure-surfacing UX, observability
**Confidence:** HIGH

## Summary

The diagnosis in ROADMAP.md is correct and now independently confirmed against Railway's own documentation: **Railway blocks outbound SMTP (ports 25, 465, 587, 2525) on Hobby/Trial/Free plans**, and even on the Pro plan Railway recommends against SMTP in favour of HTTPS-based transactional email APIs `[CITED: docs.railway.com/reference/outbound-networking]`. This is a platform-level network policy, not a credential problem, which matches every local-diagnostic result already recorded (SMTP AUTH succeeds locally, envelope probe succeeds, MX records are valid). The fix is to switch the app to Brevo's HTTP API for all outbound mail.

The codebase already has an HTTP API code path (`_send_via_api` in `email_sender.py`) and a `use_api` config flag, but it has apparently never been exercised end-to-end in production and has one latent defect worth fixing (API-key fallback to the SMTP password, which will not authenticate against Brevo's API — these are different credential types). The Brevo API contract itself (`POST https://api.brevo.com/v3/smtp/email`, `api-key` header, JSON body with `sender`/`to`/`subject`/`htmlContent`, success = HTTP 201) matches what the existing code sends, so no payload-shape rewrite is needed — only credential wiring, a defect fix, and Railway environment variables.

Separately, and regardless of transport, **every call site that sends email discards the boolean return value** (`routes.py:731`, `:783`, `:850`) and unconditionally logs `auth.verification_sent` / shows "Verification email sent!" — so a failed send is invisible today independent of the transport bug. The codebase already has the exact patterns needed to fix this (query-param flash messages, a `password.reset_*` style of distinct audit event names, a `{% if error %}` block already present but unused in `verify_email.html`, and a `results[user_id]["email"] = success` pattern already used correctly in `notifier.py`) — the fix should reuse these, not invent new ones.

**Primary recommendation:** Set `EMAIL_USE_API=true` and a real `BREVO_API_KEY` (not the SMTP password) in Railway; fix the API-key fallback defect in `email_sender.py:92`; make all three verification/resend call sites in `routes.py` check the returned boolean and surface failure via the existing query-param/audit-event patterns; add a `tests/test_email_sender.py` that mocks `requests.post` so delivery logic has regression coverage; update `RAILWAY.md` and `.env.example` to document the API variables.

### Pattern 1: Boolean-checked send with distinct failure audit event
**What:** Every existing call site currently does `await send_verification_email(...)` and discards the result. `notifier.py` already does this correctly for scheduled notifications.
**When to use:** All three verification/resend call sites (registration, unverified-login, manual resend) and ideally password reset/deletion/recovery for consistency.
**Example (existing correct pattern, to be replicated):**
```python
# Source: ra_tracker/services/notifier.py:436-445 (already correct)
success = await send_notification_email(user.email, user.id, events)
results[user_id]["email"] = success
# (caller acts on results[...]["email"] later)
```
**Example (current defect, to be fixed — routes.py:850):**
```python
# ra_tracker/web/routes.py:850-852 — discards the boolean today
await send_verification_email(user.email, user.id, user.display_name)
log_audit_event("auth.verification_sent", request, user_id=user.id,
                details={"trigger": "manual_resend"})
```

### Pattern 2: Query-param flash messages (existing convention — reuse, don't invent a flash/session system)
**What:** The app has no session-based flash/toast system. Cross-redirect messages are passed as query params and mapped to display strings in the receiving GET handler.
**Example:**
```python
# Source: ra_tracker/web/routes.py:598-621 (login_page) — established pattern
display_message = message  # From query param (e.g., after password reset)
if verified == "1":
    display_message = "Email verified! You can now log in."
elif deleted == "1":
    display_message = "Your account has been scheduled for deletion..."
```
Apply the same idea to `/verify-email` (GET) so that after a failed send-on-redirect (e.g. from `/register` or unverified login), an `?send_failed=1` style param can render the already-present `{% if error %}` block in `verify_email.html`.

### Pattern 3: Distinct audit event names for failure/edge cases (existing convention)
**What:** The audit log already distinguishes normal vs. abnormal outcomes with separate `event_type` strings within the same category, rather than a boolean field.
**Example:**
```python
# Source: ra_tracker/web/routes.py:1006, 1023, 1025 (password reset flow)
log_audit_event("password.reset_rate_limited", request, ...)
log_audit_event("password.reset_requested", request, user_id=user.id)
log_audit_event("password.reset_unknown_email", request, ...)
```
Apply the same convention: `auth.verification_send_failed` alongside the existing `auth.verification_sent`.

### Pattern 4: JSON `{status, message}` response for AJAX-style admin actions (existing convention, for reference only)
**What:** `/settings/test-telegram` and `/admin/settings/test-telegram` already return `{"status": "success"|"error", "message": ...}` based on a checked boolean. This is the established shape for JSON endpoints in this codebase, per CLAUDE.md's AJAX convention — relevant if a future admin "send test email" endpoint is added, but the verification/resend flows in this phase are full-page redirects, not AJAX, so Pattern 2 applies there instead.
```python
# Source: ra_tracker/web/routes.py:281-284
success = notifier.send_test()
if success:
    return {"status": "success", "message": "Test message sent!"}
return {"status": "error", "message": "Failed to send"}
```

### Anti-Patterns to Avoid
- **Silently swallowing the boolean return value:** the root cause of "success is reported even when nothing was sent." Every `await send_*_email(...)` call must be assigned and checked.
- **Inventing a new flash-message/session mechanism:** the codebase has a working query-param convention (Pattern 2); adding cookies/session flash for this phase would be inconsistent and unnecessary scope growth.
- **Relying on `config.email.api_key or config.email.password` as a safety net:** Brevo API keys and SMTP keys are different credential types managed in different parts of the Brevo dashboard (`Settings > SMTP & API`) `[CITED: help.brevo.com SMTP keys / API key authentication docs]`; the SMTP password will not authenticate against `api-key` header calls. Require `BREVO_API_KEY` explicitly when `use_api=True` and fail loudly (log + return `False`) if it is missing, rather than silently trying a credential that cannot work.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Calling Brevo's transactional API | A custom HTTP client wrapper | `requests.post` (already used in `_send_via_api`) | The existing implementation already matches Brevo's documented contract; no wrapper library needed for a single POST call |
| Flash messaging across a redirect | A new session-based flash/cookie system | Query-param + GET-handler mapping (Pattern 2, already used 4 times in `routes.py`) | Consistency; introducing a second flash mechanism mid-project multiplies maintenance surface for no functional gain |
| Detecting whether Railway blocks a port at runtime | A custom TCP-connect probe on startup | Don't build this — just switch to the HTTP API unconditionally in production. Railway's blocking policy is documented and plan-dependent; probing adds complexity without changing the recommended fix | Railway itself recommends HTTPS-based email for all plans, even where SMTP happens to be open `[CITED: docs.railway.com/reference/outbound-networking]` |

**Key insight:** Nothing here needs new infrastructure. Every piece of the fix (HTTP client, flash convention, audit-event convention, boolean-check convention, JSON-response convention) already exists elsewhere in this codebase in working form. The task is consistency, not invention.

## Common Pitfalls

### Pitfall 1: Assuming the SMTP password will work as a Brevo API key
**What goes wrong:** `email_sender.py:92` does `api_key = config.email.api_key or config.email.password`. If Railway only has `BREVO_SMTP_PASSWORD` set (not `BREVO_API_KEY`), this silently sends the SMTP key as the `api-key` header, which Brevo will reject (expected: 401 Unauthorized).
**Why it happens:** The fallback was presumably written to avoid requiring a second secret, on the (incorrect, for current Brevo accounts) assumption these credentials are interchangeable.
**How to avoid:** Require `BREVO_API_KEY` to be set explicitly for `use_api=True`; log a clear warning (already exists at line 95: `"Brevo API key not configured (set BREVO_API_KEY)"`) and treat "SMTP password present but no API key" the same as "not configured" rather than attempting the doomed request.
**Warning signs:** Brevo API responses logged as `401` at `email_sender.py:122` (`logger.error(f"Brevo API error {resp.status_code}: {resp.text}")`) after switching `EMAIL_USE_API=true`, if `BREVO_API_KEY` wasn't also set.

### Pitfall 2: SMTP hangs, rather than fails fast, on a silently-dropped port
**What goes wrong:** Cloud egress blocks are frequently implemented as packet drops (no TCP RST), not connection refusals. If Railway drops SYN packets to port 587 rather than rejecting them, `aiosmtplib`/`fastapi-mail`'s connection attempt can hang until an OS-level SYN-retry timeout (commonly ~127s on Linux) rather than raising an exception quickly. `_get_email_config()` does not set fastapi-mail's `TIMEOUT` field (confirmed present but unused: `ConnectionConfig.model_fields` includes `TIMEOUT` `[VERIFIED: fastapi_mail 1.6.2 ConnectionConfig fields]`).
**Why it happens:** No explicit timeout configured on the SMTP connection path.
**How to avoid:** This phase's fix (switch production to the HTTP API) sidesteps the problem, since `requests.post(..., timeout=30)` already has an explicit timeout at `email_sender.py:116`. If the SMTP path is retained as a local/dev fallback, add an explicit `TIMEOUT` to `_get_email_config()` so it fails fast rather than hanging.
**Warning signs (open question, not confirmed):** If gunicorn's worker `--timeout 120` (set in `Procfile`) killed a worker mid-SMTP-hang before the `except Exception` block in `email_sender.py` ever ran, **no `logger.error()` call would have fired at all** — which would explain why this wasn't caught by Sentry/Logtail even if those services are correctly configured. This is plausible but not verified against actual Railway logs; flagged in Open Questions.

### Pitfall 3: Verifying transport works without verifying failure paths
**What goes wrong:** Switching to `EMAIL_USE_API=true` and confirming "an email arrived" only proves the happy path. The actual bug being fixed (invisible failures) requires deliberately exercising the failure path too (e.g. temporarily wrong API key, or a mocked 400 response in tests) to confirm the UI/audit-log now shows the failure.
**Why it happens:** It's tempting to declare success once one real email is received.
**How to avoid:** Success Criteria 2 and 3 in ROADMAP.md explicitly require a *failed* send to surface as an error and be distinguishable in the audit log — plan a task that verifies this, not just the happy path.
**Warning signs:** A plan that only lists "send a real email and confirm receipt" as verification, with no negative-path test.

### Pitfall 4: RAILWAY.md / .env.example silently going stale again
**What goes wrong:** `RAILWAY.md` currently documents only `EMAIL_SMTP_*` variables and `BREVO_SMTP_USERNAME`/`BREVO_SMTP_PASSWORD` — it has no mention of `EMAIL_USE_API` or `BREVO_API_KEY`, even though both have existed in `config.py` since before this phase. `.env.example` has the same gap `[VERIFIED: read both files directly]`. If this phase changes the production transport without updating these docs, the next person redeploying or onboarding will reintroduce the SMTP-only setup.
**Why it happens:** Config flags were added to `config.py` without a corresponding docs update.
**How to avoid:** Success Criterion 5 already requires this — treat `RAILWAY.md` and `.env.example` updates as a mandatory task, not an afterthought.
